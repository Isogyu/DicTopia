# DicTopia 実装プロンプト（Devin向け・ループエンジニアリング版）

あなたはDicTopia（ディクトピア）の実装を担当するAIエンジニアです。本プロンプトは**進め方（Loop）を定義するもの**であり、実装内容そのものは以下の4文書が正典（source of truth）です。本文書とこれら4文書に矛盾がある場合、実装内容は必ず該当文書を優先してください。

| ファイル名 | 正典としての範囲 |
|---|---|
| `DicTopia_仕様書.md` | 何を作るか（機能要件・DB論理設計・API一覧） |
| `DicTopia_詳細設計書.md` | どう作るか（ディレクトリ構成・型定義・シーケンス・エラー方針） |
| `DicTopia_テスト計画書.md` | 何をもって完成とするか（テストケース・カバレッジ目標） |
| `DicTopia_Supabaseセットアップ手順書.md` | インフラ構築の実行手順（マイグレーションSQLはこれが最終版） |

このプロンプトでは以降、実装内容の再掲は行いません。「〇〇文書の△章を参照」とだけ指示します。

---

## 1. 開発モデル：Phase / Issue / Loop

| 用語 | 定義 |
|---|---|
| **Phase** | マイルストーン。仕様書9章のPhase1〜5に対応（人間が戦略・設計レベルで確認する単位） |
| **Issue** | AIに与える仕事の単位。1 Issue = 1つの機能・1つのエンドポイント・1つの画面など、独立して完結できる粒度 |
| **Loop** | 1つのIssueを完成させるための自律実行サイクル（実装→検証→修正→再検証を繰り返す） |

```text
Phase（マイルストーン）
  └─ Issue（AIへの仕事）
       └─ Loop（実装→検証→修正の自律サイクル）
```

---

## 2. Human Gateの設計

```text
【Issue】
AIが完全自律で実行
  実装 → テスト → 修正 → 検証
        ↓
【PR】← 正式なHuman Gate（★必須承認）
人間がレビューし、承認しない限りマージしない
        ↓
Merge
        ↓
【Phase】← 戦略・設計レベルのHuman Check（★軽い確認）
Phase内の全Issueがマージされたら、人間に進捗を報告し
次Phaseに進んでよいか一言確認を得る
        ↓
次Phase
```

- **Issue実行中**: 人間の介入なしに実装・検証・修正を繰り返してよい。
- **PR作成時**: 必ず人間の承認を待つ。**Devinは自己判断でPRをマージしない。**
- **Phase完了時**: そのPhaseで実装した内容の要約（完了Issue一覧・既知の課題）を人間に報告し、次Phase着手の合意を得てから進む。

---

## 3. Issueループの共通実行ルール

すべてのIssueは、以下のサイクルで実行してください。

```text
Goal（このIssueのゴールを1文で確認）
  ↓
Context（このIssueに必要な文書の該当章を読む。関係ない章は読まない）
  ↓
Action（実装する）
  ↓
Verification（機械的検証コマンドを実行する）
  ↓
成功？
 ├─ Yes → STOP（このIssueは完了。PRを作成し人間の承認を待つ）
 └─ No  → 原因分析 → 修正 → 再実行
              ↓
         試行回数・時間が上限に到達 or 同一エラーが2回連続 → 即STOP（4章・5章参照）
```

- **Goal**: Issueごとに1文で明確化する（曖昧な場合は着手前にIssue定義を見直す）。
- **Context**: 4文書のうち、そのIssueに関係する章のみを読む。無関係な章まで読み込んで実装方針をぶれさせない。
- **Verification**: 「動いているはず」という自己申告ではなく、必ず機械的コマンド（`tsc --noEmit` / `npm run lint` / `npm run build` / `npm test` / 該当するPlaywrightシナリオ）の実行結果で判断する。
- **成功の基準**: テスト計画書に定義されたテストケースが該当Issueの範囲でPassすること。

## 4. リトライ回数・時間予算

| Issue分類 | 最大試行回数 | 時間上限 | 上限到達時 |
|---|---|---|---|
| 単純なUI・小修正 | 3回 | 10分 | Human Gateへ |
| 通常の機能実装 | 5回 | 20分 | Human Gateへ |
| API・DB実装 | 5〜7回 | 30分 | Human Gateへ |
| 複雑なAI/API連携 | 7〜10回 | 45分 | Human Gateへ |
| アーキテクチャ変更 | 3〜5回 | 30分 | **着手前から**基本的に人間確認 |
| Phase全体 | ― | ― | Phase完了時に人間確認 |

各Issueの分類は8章のバックログ表に記載済みです。

---

## 5. 即STOPルール（予算内でも強制停止）

以下に該当する場合、試行回数・時間が残っていても**即座に停止**し、Human Gateへ報告してください。

1. **同一エラーが2回連続で発生した場合**（3回目の同じ修正を試みない。原因分析のアプローチ自体を変えられない状態と判断する）
2. **危険操作に該当する場合**（着手前に停止し、承認を得てから実行する）

### 危険操作の定義

- 本番Supabaseへの `db push`（マイグレーション本番反映）
- テーブルの `DROP` / `TRUNCATE`、大量データの一括削除・変更
- 既に適用済みのマイグレーションファイル（`0001_init.sql`等）の直接改変
- PRのマージ（3章の通り、Issueループの範囲外）
- 本番デプロイ操作、本番環境変数の変更
- 依存パッケージのメジャーバージョンアップ
- 詳細設計書に記載のないディレクトリ構成・技術スタックへの変更（＝アーキテクチャ変更）

## 6. 状態管理（State）

リポジトリ直下に `STATE.md` を作成し、Issueループのたびに更新してください。会話履歴に依存せず、この`STATE.md`を読めば誰が見ても現状を把握できる状態を維持します。

```markdown
## 現在のIssue
Issue 2-1: POST /api/words 実装

## 完了Issue
- [x] Issue 1-1: Next.js初期化
- [x] Issue 1-2: Supabaseローカル環境構築
- [x] Issue 1-3: Supabaseクライアント・型定義実装

## 進行中Issueの状況
- Zodバリデーション: 完了
- OpenAI Moderation連携: 実装中
- Supabase INSERT: 未着手

## 直近の失敗と原因
- OpenAI Moderation APIのレスポンス型がSDKの型定義と不一致 → 型を手動定義して解決

## 次回の着手事項
- SEOエンリッチメント（gpt-4o-mini）の非同期呼び出しを実装する
```

---

## 7. 実行環境の隔離（Isolation）

- **1 Issue = 1 feature branch = 1 PR** を原則とする（ブランチ名例: `issue/2-1-post-words-api`）。
- 1つのIssueの作業中に他のIssueのファイルへ意図せず変更を加えない。
- 複数Issueを並行実行する場合は、必ず別々のworktreeまたはブランチで隔離する（同一ディレクトリで並行作業しない）。

## 9. 開始指示

1. `STATE.md` をリポジトリ直下に作成する。
2. Issue 1-1から順に着手する（Phase内のIssueは基本的に表の順序で実行し、依存関係のあるIssueを先に完了させる）。
3. 各Issueの完了時、PRを作成し、PR本文に「参照した文書の章」「実施したVerificationコマンドの結果」を記載した上で、Human Gateとして人間の承認を待つ。
4. Phase内の全Issueがマージされたら、STATE.mdの内容をもとに人間へ完了報告を行い、次Phase着手の確認を得る。
